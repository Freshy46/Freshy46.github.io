Kyron SMP store

The storefront for a Java 1.21 server — twelve ranks across two game modes, gift cards, Stripe checkout and a live player count. Then built four more times in four different visual directions, off the same data, so the owner could pick one by looking at it rather than by describing it.

What's on it

Nine SMP ranks from £1 to £10, three FFA ranks, and two gift card denominations. Every rank carries the same four perks — custom prefix on tab, a rank kit, a chat tag and a Discord role — so the page has to sell the difference between them on identity rather than on a feature list. The £1 tier lets you write your own prefix, subject to staff approval.

Around the store: a hero with the live player count and a one-click IP copy, a "what happens after I pay" section, gift card redemption steps, the rules, and the terms and privacy pages a payment processor expects to see. Light and dark toggle throughout.

How it works

One data file, five complete rebuilds

Every rank, price, checkout link, perk list, colour code and blurb lives in a single data.js that assigns one object to window.KYRON. Nothing is written into the markup. Each theme reads that object and renders itself from it.

window.KYRON = {
  ip: "kyron.mygame.host",
  version: "Java 1.21+",
  perks: ["Custom prefix on tab", "Rank kit", ...],
  ranks: [
    { name: "Flame", price: 2.50, tag: "Flame",
      colour: "#FFAA00", mc: "&6", blurb: ... },
    ...
  ]
}

Each rank carries its hex colour and the Minecraft colour code the prefix actually renders in, so the chat preview on the site shows the tag in the same colour the player will see it in game. Getting that wrong is the fastest way to a refund request.

A price change is one number, once. Five themes follow. That mattered more than it sounds like it should: the whole point of building five was that the client could change their mind about the look without anyone re-entering nine ranks by hand.

Why five versions, and what each one was testing

Asking someone to describe the site they want gets you adjectives. Showing them five finished sites gets you a decision. Each one commits properly to a direction rather than hedging, and each lays the ranks out differently, because the rank list is where the whole page lives or dies.

Taking money without a backend

The site is static. There is no server holding card details, no database of orders, and nothing of mine sitting between a player and their bank — checkout is a Stripe Payment Link per product, so the card form is Stripe's page on Stripe's domain.

For a server store that's the right trade. The alternative is running a payment backend for the sake of eleven fixed-price products, and taking on the liability that comes with it. This way the riskiest thing the site does is redirect.

What that leaves is the part players actually get confused by: what happens between paying and having the rank. So the page answers it directly — a "what happens after I pay" section, gift card redemption steps written out, and a support email on every page. Most store tickets are that question, and answering it on the page is cheaper than answering it eleven times a week.

Live player count

The hero shows how many people are on right now, which is the single most persuasive thing a server store can put above the fold, and the fastest way to look dead if it breaks. It degrades to the plain IP rather than to a zero or a spinner when the query fails.

Next to it, one button that copies the IP to the clipboard — kyron.mygame.host, with the raw 46.249.47.73:25006 as the fallback for clients that don't resolve the hostname — and one that opens the Discord. Those two buttons are what the page is for; everything else is underneath them.
