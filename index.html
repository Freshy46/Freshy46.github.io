A voice assistant I built and gave a real interface to. You talk to it, it talks back, and it can actually do things — read and write files, search the web, take notes, work through a study plan or a schedule. Seventy-five tools behind one conversation.

Gemini Flash-Lite · speech in / voice out · 75 tools · persistent memory · custom HUD

What it does

It listens, it answers out loud, and it remembers. Speech goes in, the language model decides whether it needs a tool to answer properly, and the reply comes back as synthesised voice as well as on screen. Memory persists across sessions, so it holds context from things you told it days ago rather than starting cold every time.

The row along the bottom switches what it's set up to do. Each mode changes what it has access to and how it behaves, rather than just filtering a menu:

ModeWhat it's for
STUDYWorking through material — explanations, questioning you back, tracking what you've covered
PLANNINGSchedules, task breakdowns, working out the order things need to happen in
SYSTEMThe machine it's running on — diagnostics, resource use, the state on the side panels
WEBSearching and pulling in things it doesn't already know
FILESReading and writing on disk
NOTESCapturing things mid-conversation without breaking out of it
CHATPlain conversation with no particular job attached
SETTINGSVoice, model, mode and memory configuration
STANDBYDrops it to idle without shutting it down

The interface

The interface was as much of the work as the assistant behind it. A voice assistant with no screen gives you nothing to look at while it thinks, and no way to tell the difference between working, waiting and broken. So everything it's doing is on the wall.

The sphere in the middle is the assistant itself — thousands of particles that react to what it's doing, so idle, listening, thinking and speaking all look different from across the room. Around it, four groups of live readouts:

PanelShows
SYSTEM DIAGNOSTICSCore load, memory allocation, GPU thermal, uptime
NEURAL ACTIVITYSynaptic rate, GPU load, VRAM, and whether inference is idle or running
VOICE PROCESSINGLive input waveform, signal strength, and recognition state
NETWORK TRAFFICUp and down throughput, packets per second, latency
ACTIVE MODULESLanguage model, voice synth, speech input, link, mode, encryption
ENVIRONMENTAmbient temperature, pressure, location, conditions

The status block in the corner is the one that matters day to day — mode, whether the voice is currently speaking, whether memory is on, how many tools are loaded, which model is answering, and round-trip latency. When something feels slow, that block tells you whether it's the model, the network or the speech layer without opening a log.

Decisions

Why Flash-Lite and not the biggest model available

It's a voice assistant, so the thing being optimised is the gap between you finishing a sentence and it starting to answer. Past about a second that gap stops feeling like a conversation and starts feeling like a form submission, and no amount of extra answer quality buys that back.

Flash-Lite is the cheapest, fastest tier, which is the right default for the overwhelming majority of what gets asked — a question, a reminder, a file, a lookup. The model is exposed in settings rather than hardcoded, so anything that genuinely needs more reasoning can be moved up deliberately instead of everything paying for it all the time.

Seventy-five tools behind one conversation

The assistant isn't a chat window with a search box bolted on. It has real capability — the filesystem, the web, notes, system state — and the model picks which one it needs rather than the user picking a feature first.

That's the whole design bet: you shouldn't have to know which mode a request belongs to before you make it. Modes exist to shape behaviour and narrow the tool surface when you already know what you're doing, not as a menu you have to navigate before you're allowed to ask a question.

Memory that survives the session

Memory is on by default and persists between runs, which is the difference between an assistant and a search bar. It's a toggle rather than a permanent fixture — it's on the settings panel and the status block always shows whether it's enabled — because an assistant that quietly remembers everything and never tells you is a worse thing to live with than one that forgets.

Crysgear

Cores and Aspects. A full combat-ability system. Four elements, three tiers, fourteen abilities, and gear you can infuse them into.

  • Stack Java 21, Paper 1.21
  • Size 38 classes
  • Includes custom items, resource pack, ability engine, GUIs

Cores and Aspects for Crysgear SMP. A combat system built around one item you carry, four elements you can put inside it, and the choice of whether to keep that power in your hand or burn it into your gear.

Java 21 · Paper 1.21 · 38 classes · custom resource pack · no database

The idea

A player carries a Core. The core holds one Aspect at a tier from one to three. There are four aspects — Strength, Mirror, Light and Fire — and each one gives you passives that are always on plus abilities you fire by clicking with the core in hand. Higher tiers don't just scale numbers; they unlock new abilities and move the old ones onto different click slots, so a tier 3 player has a genuinely different kit from a tier 1 player.

Then there's the second decision. You can infuse an aspect into a sword or a piece of armour. When you do, the core goes quiet — you lose the whole ability kit — and the gear takes over with its own passives and, at tier 3, its own ability. It's a real trade rather than an upgrade: burst power in your hand, or something quieter that works while you're holding a weapon.

How it works

Adding a fifth aspect takes three lines

Aspects are registered into an EnumMap<AspectType, AspectHandler> at startup. Every other system in the plugin — the HUD, the cooldown tracker, the core GUI, the item lore builder, /cores info, both tick loops — goes through that registry rather than switching on a type. So a new element is one enum constant, one class implementing AspectHandler, and one register() call. Nothing else has to be told it exists.

// onEnable registry.register(new StrengthAspect(...)); registry.register(new MirrorAspect(...)); registry.register(new LightAspect(...)); registry.register(new FireAspect(...));

aspect/AspectRegistry.java · aspect/AspectHandler.java · Crysgear.java

There is no database — the item is the save file

Nothing about a player's aspect is stored server-side. The aspect id, its tier, the stored tier for a withdrawn aspect and the infusion flag all live in the item's own PersistentDataContainer, under namespaced keys registered once at startup.

That buys a lot for free. State survives restarts without a save routine. It survives a world transfer or a server move, because it's inside the item file Minecraft already writes. Hand the core to someone else and the power goes with it, which is exactly the behaviour you want on an SMP — cores get looted, traded and fought over as objects, rather than as a row in a table with someone's name on it.

The same container drives the visuals. CustomModelData is computed from the aspect type and tier, so the resource pack shows a different model for each of the twelve aspect-and-tier combinations, plus the empty core, without the plugin knowing anything about textures.

modelData(tier) = baseModelData + (tier - 1) STRENGTH 8101 MIRROR 8201 LIGHT 8301 FIRE 8401

The cost is the obvious one: if an item can be duplicated, the state duplicates with it. That's why every GUI in the plugin works on clones and writes back deliberately, rather than moving the real stack around inside an inventory the player can reach into.

item/Keys.java · item/CoreItems.java · aspect/AspectType.java · util/Clones.java

Two tick loops, and why the slow one isn't enough

Passive effects, infusion sweeps and the cooldown display run every 10 ticks — half a second. That's plenty for reapplying Strength or checking whether someone still has the right armour on, and it keeps the per-player cost low on a full server.

Anything that has to track movement gets its own loop at one tick. A charging fireball grows and follows the aim; Light's runes stay angled where the player is looking; Mirror's afterimage has to be in the right place the moment it's struck. At half-second granularity all of those visibly stutter.

Both loops resolve the aspect the same way, and both fall back to the stowed core rather than the held one. That's deliberate: an ability already in flight has to keep running after you switch to your sword. Putting the core away shouldn't cancel a fireball that's already in the air.

Crysgear.java — runTaskTimer at 10L and at 1L

Which aspect is actually active

At any moment a player might have a core in the main hand, a core in the off hand, an infused sword, infused armour, or several of those at once. Everything that fires an ability, draws the HUD or checks a cooldown asks one method which aspect is live, and gets a single answer.

The rule: infused gear wins. If an aspect has been burned into gear it has left the core, so the core stops acting entirely and the infused item is the only thing that can. If nothing is infused, the core has to be in one of your two hands. Sitting in your inventory does nothing.

The part that took the most care is that the infusion flag lives on the core, not on the sword — one authority — and a background sweep keeps the two honest when a player drops the gear, dies, or has it broken. Two independent sources of truth about whether something is infused is exactly the kind of thing that drifts apart on a live server and ends with someone holding the sword bonuses and the full core kit at the same time.

The resource pack

Crysgear ships its own pack rather than reusing vanilla items with a rename. It carries a model and texture per aspect per tier, driven off the custom model data above, and a bitmap font used to draw ability icons inline in chat and on the action-bar HUD — so a cooldown readout shows the actual ability glyph instead of a letter.

The build script compiles the plugin and zips the pack side by side, so a release is always a matched pair. A jar that ships without its pack shows everyone a stick.

AegisStaff

The whole staff side of a server. Punishments that escalate on their own, staff mode, reports, and an audit log that watches the staff too.

  • Stack Java 21, Paper 1.21
  • Size 124 classes, 40+ commands
  • Storage SQLite or MySQL
  • Extras Discord feeds, web panel

The whole staff side of a server in one plugin. Punishments with an escalation ladder, staff mode, vanish, freeze, reports, notes, an audit log of what staff themselves have been doing, Discord feeds and a local web dashboard.

Java 21 · Paper 1.21 · 124 classes · SQLite or MySQL · zero dependencies · v3.0.0

It's the largest thing on this site. Forty-odd commands, five staff ranks, its own database layer, and a set of rules designed around the assumption that the people using it can also abuse it.

The five ranks

Ranks stack downward — each one includes everything below it, and a person gets exactly one. They're composed in LuckPerms rather than hardcoded, because every single feature is its own permission node and every node defaults to false. Nothing is implicit, and a server that wants a different shape of team can build one.

RankGains
HelperChat moderation and reports. Warn, kick, mute, tempmute, the punish GUI, player history, notes, staff chat, staff mode. No inspection tools and no bans
ModTempban, unmute, unwarn, the ban list, spectate, /tphere, direct player alerts, resolving reports
AdminFreeze, /tp, the staff audit GUI, deleting notes and reports. First rank that can review other staff — and the first that's punish-exempt and freeze-exempt from them
ManagerPermanent bans, unbans, IP bans, IP addresses visible in /seen, and forcing another staff member off duty
Head ManagerVanish including on others, silent join and quit, config reload, diagnostic dump

A deliberate gap: mods can pull a player to them with /tphere but cannot /tp to a player. Teleporting to someone lets you drop into a fight or a base unannounced; pulling them to you doesn't. That distinction is the difference between a moderation tool and a way to cheat at survival.

Three commands sit on no rank at all — /invsee, /endersee and /spawnstash. They're op-only and have to be granted by hand, one player at a time, because reading someone's inventory is a different category of power from muting them.

Every punishment takes an optional -s flag to issue it silently, so a ban during an event doesn't have to become an announcement. Any command that clashes with another plugin can be switched off in config, and /staff <command> always works regardless of what else is installed.

How it works

Punishment guidelines as config, and a ladder that escalates on its own

The feature I'd point at first. Staff don't decide durations — they name what happened, and the plugin works out the punishment.

/offend <player> <offence> looks the offence up in a guidelines file that holds its type (ban, mute, kick or warn), what a first offence costs, whether it's severe enough to always be permanent, shorthand aliases staff can type instead of the full id, and a category for browsing. The plugin then applies it, and escalates repeat offenders by itself.

The ladder is keyed by which number punishment it is, and only the numbers that change need listing — set 2 and 5, and punishments 2 through 4 all take the first value while 5 onward take the second. Bans and mutes count separately, so someone who talks too much never creeps toward a ban. Every ban counts toward the ladder, including expired ones, lifted ones, and ones typed by hand.

What this buys is consistency. The oldest problem in server moderation is two staff members handing out wildly different punishments for the same thing, and every argument that follows. Encoding the guidelines means the answer doesn't depend on who was online. /offend is still gated by the permission for whatever punishment it would issue, so a helper naming a bannable offence doesn't get to issue a ban through the back door.

Staff mode: on duty is a different mode of play, not a hat

Going on duty puts you in spectator and stores your inventory. Coming off duty returns you to spawn and gives it back. While you're on duty you cannot change gamemode.

No staff command works off duty. Not one — and being op doesn't bypass it. The only exception is /report, which any player can use. That single rule is what stops the staff toolkit leaking into normal play, and it means "was this person on duty" is always a meaningful question with a recorded answer.

Creative mode is blocked for anyone not on an explicit bypass list, which closes the other obvious route to the same problem.

Combat locks staff out of their own tools

For fifteen seconds after another player hits you, every staff command is refused. Including /staffmode — especially /staffmode, because going on duty was the escape route. Only /report still works.

Without this, staff tools are an "I win" button in a fight: you're losing, you vanish or flip to spectator, and you take nothing. The lock means a staff member in a fight is a player in a fight until it's over.

The same combat tracking punishes ordinary combat logging. Disconnect within the window of trading blows and you're punished automatically — routed through the offence system, so it uses the same published guidelines and the same escalation ladder as everything else rather than being a special case bolted on the side.

Watching the staff, not just the players

Most staff plugins record what was done to players. This one also records what staff did, and puts it in front of the rest of the team.

Every staff action goes into an audit log, browsable in a GUI by admins and above. On top of that sits a bias check: if a staff member punishes someone they were fighting inside the last minute, the rest of the team is warned about it automatically. Nothing is blocked — the punishment still lands, because sometimes the person you're fighting genuinely is cheating — but it can't happen quietly.

There's also a weekly digest posted to Discord summarising what each staff member did. Both features exist because the failure mode on a real server is almost never a staff member who can't find the ban command; it's one who uses it on someone they lost a fight to.

The permission structure backs this up. Admins and above are punish-exempt and freeze-exempt, so the tools can't be turned sideways on the people meant to be reviewing them.

Storage: SQLite by default, MySQL when you actually need it

Default is SQLite, and it needs no setup whatsoever — Paper already ships the driver, and the database is one file in the plugin folder. Drop the jar in, restart, done. MySQL is there for the one case that genuinely requires it: several servers sharing one punishment list.

Access goes through a set of DAOs — punishments, reports, notes, profiles, player state, audit — over a versioned schema, so a table change is a migration rather than a wipe.

Two things sit on top of that. Unknown names can be looked up against Mojang, so someone can be banned pre-emptively before they've ever joined. And on first start it can import punishments and player records from an older FreshStaff v2 install — reading that folder only, never moving or changing anything in it, so the old install stays a working rollback if the migration goes wrong.

The whole plugin ships with no shaded libraries at all. Paper provides Adventure, the annotations and the SQLite driver, so the jar in the plugins folder is the entire plugin.

Four Discord feeds, none of which can lag the server

Punishments, reports, staff actions and staff chat each post to their own webhook, so they can go to four different channels with four different sets of people able to read them. Staff chat in a channel the team can reach from their phones; punishments somewhere players can see them; the audit feed somewhere only management looks.

Leave a URL blank and that feed is simply off — there's no separate enable toggle per feed to get out of sync with itself.

Everything posts asynchronously. A webhook that's been deleted, or a Discord outage, cannot slow the server down or stop a punishment going through. The ban lands whether or not anyone gets told about it, which is the correct priority.

A dashboard that can't be reached from the internet

There's a read-only web panel for the owner, and it binds to 127.0.0.1 — not 0.0.0.0. It's reachable from the machine the server runs on and from nowhere else: not the LAN, and not the internet even if someone forwards the port.

That's a deliberate ceiling on the blast radius. A staff panel holding punishment records, IP addresses and player notes is a genuinely attractive target, and the safest version of that is one that was never listening on a public interface in the first place. An optional token can be required in the URL for anyone who wants to tunnel to it.

The bait chest

/spawnstash builds a decoy stash from a schematic — a convincing little base with chests in it, placed to catch people who are stealing from others. The plugin reads and pastes the structure itself, including the block entities, rather than depending on a world-edit plugin being installed.

It's op-only and granted by hand, like the other inspection tools.

How it was tested

Staff tooling is miserable to test by hand. Half the features need a second player, several need that player to do something specific at a specific moment, and the interesting cases are the ones where someone disconnects at exactly the wrong time.

So the tests are scripted. A headless Minecraft client connects to a local server and plays out each scenario — get hit and then try to open staff mode, log out mid-fight, tunnel downward, walk into a frozen state, click through a GUI — while watching what the server sends back. Around twenty of them, one per scenario, each runnable on its own.

It means the awkward paths get exercised on every build instead of the first time a player finds them.

Messages and configuration

Every piece of player-facing text lives in its own messages file, separate from configuration, so retheming the plugin for a server never means touching a setting. Durations use one format everywhere — 30m, 14h, 2d, 1w, perm — in commands, in the guidelines file and in the GUI presets alike.

Also built

The biggest thing I've built. Players found towns, claim land, run a treasury, tax their citizens, sign alliances and go to war over borders. A server-wide political layer sitting on top of survival.

Java · Paper · land claims · economy · warfare

What it does

A player founds a settlement and claims the land around it. Inside those borders they decide who can build, who can break and who can come in at all. Outsiders can't touch it.

From there it stops being about blocks. A civilisation has a treasury, and it fills it by taxing the people who live there. It has neighbours it can trade with, ally with, or refuse to speak to. And when diplomacy fails it can declare war, and territory changes hands — the borders on the map are the scoreboard.

How it works

Claims are a permission system pretending to be a map

Underneath the borders, every claim is answering one question thousands of times a second: is this player allowed to do this here? Every block placed, every block broken, every chest opened, every piston, every explosion, every fire tick inside claimed land has to be checked against who owns it and what that person's relationship to the owner is.

Which means the answer has to be cheap. Claim lookups sit in the hottest path in the whole plugin — they run on events that fire constantly, on every player, forever. Everything else in the system can afford to be clever; this part has to be fast, and it has to be right, because the moment claim protection is wrong someone loses a base.

War is the interesting problem, because it has to break the rules

Claims exist to say no. War exists to say sometimes yes. The entire protection system is built to stop outsiders touching your land, and then war has to carve a hole in exactly that, for exactly the right people, for exactly as long as the war lasts.

That's the tension the whole feature lives in. Open it too far and a declaration of war becomes a griefing tool — declare, level someone's town, walk away. Keep it too closed and war is two people hitting each other in a field while the borders never move and nothing is at stake.

The answer has to make territory the thing you win and lose, so the fighting has a point beyond the fight, while leaving the loser with a civilisation still standing at the end of it. A player who logs off after a war having lost land will be back. A player who logs off having lost everything they built will not.

Taxes are the part players feel most

An economy where money only ever comes in isn't an economy — it inflates until the numbers stop meaning anything. Taxes are the drain that keeps the treasury worth filling and gives leadership an actual decision to make.

It's also the most politically loaded thing in the plugin. A tax rate is a leader making a decision that costs their citizens something, and citizens can leave. That single number does more to generate server drama than every other feature combined, which is precisely why it's in there.

Become a block. Any block, anywhere — or in a round of prop hunt, where one team hides in the scenery and the other team has to work out which crafting table is breathing.

What it does

Turn into a block and you stop being a player-shaped thing standing in a room. You become part of the room. Pick the right block and stand somewhere it belongs and people walk past you — which is the entire game.

Two ways to use it. Free roam: morph anywhere on the server, whenever you like, and use it however you want — ambushes, hiding, or just being a very confusing chest. Prop hunt: a proper round with hiders, seekers and a clock.

Same three-command shape as Morph, for the same reason: the whole appeal is picking a spot and committing to it before anyone arrives, and a menu would cost you the seconds that decide whether it works.

The rules that make it work

Two design decisions carry the whole thing, and they're both about taking something away from the player who's hiding.

RuleWhy it's there
You're locked in placeMovement is what gives a hider away, so removing it makes the disguise nearly perfect — and makes committing to a hiding spot a real decision you can't take back
You're a solid blockPeople bump into you, stand on you and try to break you. The disguise has to survive being touched, not just being looked at

How it works

Being solid is what makes it a game instead of a costume

A disguise you can walk through is a cosmetic. The moment a seeker's first instinct — run at the suspicious block and see what happens — actually collides with something, the disguise is load bearing, and it can be tested, probed and caught out.

It cuts the other way too. Being solid means a hidden player changes the shape of the map: they can be stood on, they can plug a gap, they can be in the way. A hider who picks a spot that makes the room subtly wrong gets found, and that's a skill worth having.

Locked in place is a cost, not a limitation

Being unable to move is the price of being almost invisible, and the trade is what makes the hiding interesting. You commit before the seekers arrive, and once you're committed you can only sit there and find out whether you chose well.

It also removes the failure mode that ruins prop hunt: a hider who can move freely just runs away forever and the round never ends. Taking movement away means the round always resolves — either they're found or the clock runs out.

Blending in is on the player, not the plugin

The plugin's job is to make you a convincing block. Whether you're a convincing block in that spot is on you. A stone brick in a stone brick wall is invisible. The same stone brick alone in the middle of a wheat field is a person, and everyone knows it.

That's deliberate — it's where the skill lives. If the plugin picked a sensible block for you the game would play itself, and the fun of watching someone stare directly at you from two blocks away would be gone.

Turns a player into a mob. Pick a form and everyone on the server sees a zombie, a creeper, an enderman — walking around, doing whatever you're doing.

Java · Paper · Minecraft plugin

What it does

You choose a mob and you become it. Not a skin on a player model — other players see the actual mob, moving where you move, doing what you do. Your own view stays normal so you can still play; it's everyone else's screen that changes.

The point is the reaction. A zombie that stops and looks at you does not read as a mob for very long, and the moment someone works out that one of the mobs in the room is a person, the whole space changes. That's a fundamentally different experience from a cosmetic that only changes what you look like standing still.

Three commands, and that's deliberately the whole surface. There's no menu to learn and no setup — you type what you want to be. Anything more would get in the way of a feature whose entire appeal is how fast you can use it.

How it works

Your screen and everyone else's screen disagree, on purpose

The morphed player has to stay playable. If you replace someone with a mob on their own client too, they lose their hands, their hotbar and their camera, and the feature stops being usable for anything except standing still and being looked at.

So the illusion is built for other people. The morphed player keeps a normal first-person view and normal controls, while everyone else's client is told there's a mob there instead. Two versions of the same player, and the only one that has to be convincing is the one you can't see yourself.

The hard part is everything that isn't standing still

A static disguise is easy. Keeping it right through movement is where the work is — the form has to follow every position and rotation update, survive sprinting, sneaking, swimming and falling, and handle the moments where a player does something a mob has no animation for.

Then there's every other system that assumes a player is shaped like a player: combat reach, hitboxes, nametags, what happens when you take damage, and what other people see when you die. A disguise that breaks the first time someone hits you is worse than no disguise, because it teaches people exactly how to test for it.

Physical crates and keys for Kyron FFA. Bind a crate to any block in the world, build its loot table in a menu, and let players spin it. Built so an admin never has to open a config file and a player never loses a key they paid for.

What it does

A crate is a real block — a chest, a beacon, whatever you're looking at when you run the command. A hologram floats above it. Right-click it holding the right key and the key is consumed, the roulette spins, and the prize goes into your inventory, or onto the floor at your feet if it's full. Right-click without a key, or left-click at all, and you get the reward preview with the real odds instead of a guess.

Keys are tagged with the crate id in NBT, so a renamed lookalike opens nothing. They can't be placed as blocks. They drop on death like any other item — which is the entire point on an FFA server, where a key in someone's inventory is a reason to fight them.

Placed crate blocks can't be broken, blown up, or moved by a piston.

How it works

The editor is the config file

crates.yml exists, but nobody is meant to open it. It's an output. Everything about a crate is built in a menu instead.

The top four rows are the loot table. Pick an item up in your inventory and click an empty slot to add it as a reward, or shift-click it straight across. Click a reward with an empty cursor to remove it. A comparator toggles into odds mode, where clicking a reward raises or lowers its weight — left for +1, shift-left +10, right −1, shift-right −10 — and the live chance percentage updates on every item in the table as you go. Weights are relative, so a reward at 10 is ten times as likely as one at 1, and you never have to make them add up to anything.

Next to the name tag is the key slot. Drop any item in there and it becomes this crate's key, keeping its name, lore and enchants. Leave it alone and it uses the default. There's a toggle for whether a win from this crate broadcasts to the server.

Closing the menu saves. So does a plugin disable while the editor is open, which is a two-line guard that stops a server restart eating twenty minutes of loot-table work.

Every slot in that menu holds a copy. Nothing ever leaves or enters your real inventory while you're editing. That isn't a detail — it's the whole reason the editor can exist. An admin menu that moves live item stacks around is a dupe waiting to be found, and on an FFA server it will be found.

gui/EditGui.java · gui/WeightsGui.java · crate/Reward.java

The spin is theatre — the winner is already decided

The prize is rolled from the weighted table before the menu even opens. The animation is handed that result and its only job is to arrive at it convincingly.

It's a 27-slot inventory with a nine-slot strip across the middle row. Every step shifts the strip one slot left and feeds a new random reward in at the right-hand end. The real prize is inserted at exactly the step that leaves it coasting into the centre slot on the final shift. The gap between steps stretches as it goes — one tick, then two, then four, seven, eleven — so it slows into place rather than stopping dead.

step 0-19 20-29 30-35 36-39 40+ delay 1t 2t 4t 7t 11t

Because the outcome is fixed up front, the animation is disposable. It can be cut short at any frame — by a close, a disconnect, or the server going down — without changing what the player wins or leaving the outcome undecided.

A consumed key is never left unpaid

The key is taken from the player's hand only once the spin has actually started, so a failed open — wrong key, unknown crate, no rewards configured — costs nothing.

From that moment the plugin owes them a prize, and there are three ways the spin can end: it finishes normally, the menu closes, or the plugin disables underneath it. All three route into the same award() method, which guards on a flag so it can be called from anywhere, more than once, in any order. Whichever path gets there first pays out; the rest do nothing.

If the inventory is full the prize drops at the player's feet rather than vanishing. The win message uses the reward's real display name where it has one and falls back to the item's translation key where it doesn't, so it reads correctly in whatever language the client is set to. Broadcasts are per-crate, so a common crate doesn't spam chat.

gui/SpinGui.java award() · listener/GuiListener.java onClose · KyronCrates.java onDisable

Holograms that can't be orphaned

Floating crate text is the classic way to leave permanent litter in a world. Entities get saved into the chunk, the plugin gets removed or crashes before it can clean up, and the text stays there forever with nothing left that knows how to delete it.

These are non-persistent display entities. They're never written to the region file at all — they're spawned when the chunk loads and destroyed on disable. A hard crash leaves nothing behind, because there was never anything on disk to leave. Remove the plugin entirely and the world is clean the moment it next loads.

Catches base-hunters two ways at once. It scores players on how they mine to spot the ones hunting rather than digging, and it stops ESP clients seeing underground bases at all — server-side, so no cheat client can work around it.

Java 21 · Paper 1.21 · behavioural scoring · server-side anti-ESP · anticheat bridge

The problem

On a survival server the thing that ruins bases isn't combat, it's people finding them. Two ways that happens: someone runs a cheat client that draws chests through walls, or someone just tunnels methodically downward across the map until they hit something.

An anticheat catches the first if the client is one it knows about. Nothing catches the second, because digging down isn't cheating — it's just mining, done with intent. This plugin goes after both.

/espsus

aliases /sus and /suspects · opens the suspect list, spectate or dismiss from it

How it works

Scoring the shape of someone's mining

The signal is a descent: a block broken directly beneath the player. Doing that once is completely normal. Doing it over and over in a row is the pattern people use when they're sweeping for someone else's base rather than actually collecting anything.

So each descent adds a point — but once a run of consecutive descents passes a streak length, every further one is worth several times more. That multiplier is the whole heuristic. It's what separates "dug down to a cave" from "systematically tunnelling", without needing to know anything about the player's intent. Breaking anything that isn't below you resets the streak.

Points bleed away every minute, so ordinary mining fades to nothing and only sustained behaviour accumulates. Cross the score threshold and you land on the list.

There's a second, independent rule for volume: a large number of descents within a rolling window puts someone on the list on its own, whatever the decaying score happens to be doing. Digging at that rate for that long isn't ordinary mining regardless of how it's scored.

Falling and soft blocks — gravel, sand, dirt, grass, water, lava — are ignored entirely, since they aren't tunnelling and would otherwise generate constant noise.

Anti-ESP that a cheat client can't defeat

The important part: the client is never sent the data. This isn't obfuscation or a client-side check that a modified client can ignore — the information simply doesn't leave the server, so there is nothing for a cheat to read.

To anyone above ground, containers and spawners below a depth threshold are sent as plain stone, and deepslate below Y=0 so the fake block never looks out of place for the depth it's at. Item frames, armour stands, minecarts, dropped items and mobs below the threshold aren't sent at all. Everything is restored the instant a player descends past the threshold themselves — so the base owner sees their own base normally, and only someone hovering above it is looking at a lie.

The concealed list is the set of things base ESP actually hunts for: chests, barrels, shulkers, hoppers, furnaces, brewing stands, beacons, spawners, trial spawners, vaults. These are found through the chunk's block-entity list, which is also its limitation — plain blocks like ores don't have block entities, so hiding those is Paper's own anti-xray's job, not this plugin's. The config says so directly rather than letting someone add ores to the list and assume it worked.

A margin above the threshold stops the effect flickering for someone hovering right on the boundary, and the conceal radius is meant to sit near the server's view distance — going wider costs work for no benefit, since the client isn't sent those chunks anyway.

Players are never hidden, because hiding them would break PvP and look like a bug. The ender dragon and the wither are never hidden either.

Suspects never learn they're suspects

Alerts are hidden from the person they're about, even if that person holds the alert permission themselves. Staff get pinged when someone is added, and pinged again each time an already-listed player climbs another chunk of score.

This matters more than it sounds. A watchlist that tells you you're on it converts a detection tool into a training tool — the person adjusts their pattern, stays under the threshold, and you've taught them exactly where the line is. The config note for the setting says to turn it off only while testing alone, since otherwise you flag yourself and see nothing.

There's an exempt permission for players who should never be listed at all.

One list, two kinds of evidence

If AxyronAC is installed, the plugin pulls violation levels out of it so anticheat verdicts sit in the same list as the mining heuristics. A high enough total across all checks puts someone on the list on anticheat evidence alone, and individual checks that are noisy on a given server can be ignored without silencing the rest.

It's a soft dependency. With no anticheat present the plugin carries on as a pure mining watchlist rather than failing to load — the integration is a bonus, not a requirement.

Having both in one place is the point. Neither signal is conclusive by itself; someone who trips the anticheat occasionally and tunnels like a base-hunter is a much stronger case than either on its own, and that's only visible if they're on the same screen.

Everything is tunable, and the config explains itself

Points per descent, streak length and bonus, the threshold, the decay rate, the volume rule, the depth cutoff and the ignored blocks are all configurable — because the right numbers depend on the server. A skyblock server and a 5000-block-radius survival map have completely different ideas of what normal mining looks like.

Each setting carries a comment explaining what it's for and what changing it does, including the ones where the obvious change is wrong. The depth cutoff defaults to counting everything, with a note explaining why: base-hunters start digging from wherever they're standing, and spawn can easily be high up a mountain, so a "sensible" lower cutoff would miss them.

There's a debug mode that logs why each individual block break was or wasn't counted, for tuning the thresholds against a real server's mining habits rather than guessing.

Ranks and permissions without LuckPerms. Four roles out of the box, a coloured star next to every name, per-player permission grants, and a config you can read in one sitting.

Why it exists

LuckPerms is excellent and most servers only ever use a tenth of it. Contexts, tracks, inheritance graphs, MySQL sync, a web editor — powerful, and all of it sitting on a server whose actual requirement is "give staff a blue name and let them run a few commands".

This does that part and stops. Four roles, a permission list per role, per-player grants on top, and a name colour. One config file, no database, nothing to install alongside it.

How it works

Inheritance is a list, not a graph

LuckPerms resolves inheritance at runtime — a group points at its parent, that parent points at its own, and the effective set is computed by walking the tree. Powerful, and the reason a misconfigured setup can be genuinely hard to debug.

Here each role simply lists every permission it has, including the ones it shares with the roles below it. Owner's list contains the dev, staff and member nodes explicitly. It's more typing and it duplicates entries — and in exchange, what a role can do is the list next to its name. There is no resolution step to reason about and no way to be surprised by an inherited node you forgot about.

That trade only works because the list is short. At forty roles it would be unmanageable, and at that size you should be running LuckPerms.

Permissions are attachments, rebuilt from scratch every time

Bukkit grants permissions through attachments, and the easy mistake is to add them incrementally and lose track — a stale attachment keeps granting a permission long after it should have gone.

So nothing is ever adjusted in place. Every refresh removes every attachment the plugin is holding for that player, then rebuilds the whole set from their role plus their personal grants. Applying a change and applying it for the first time are the same code path, which means the state after a change can't drift from what a fresh login would produce.

Attachments are tracked per player and dropped when they disconnect, so a long-running server doesn't accumulate references to people who left hours ago.

The star is the point

A permission plugin nobody can see is a permission plugin nobody values. The visible half is a coloured star and role label in front of the player's name, applied to both the tab list and their display name, in the role's own hex colour.

It's the same reasoning as ranks on a store page: people pay for, and care about, the part that other players can see. The permission nodes are what the plugin does; the star is what it's for.

One caveat worth stating plainly: this sets the player's display name, so a chat plugin that builds its own format from scratch will ignore it. On a server already running a chat formatter, the star shows in tab and the chat format stays that plugin's job.

Storage is a flat file, on purpose

Role assignments and per-player permissions live in a data.yml next to the config, written on every change. No database, no connection pool, no driver to install.

For a single server with a normal player count that's the right answer — it's readable, it's editable by hand in an emergency, and it backs up by being copied. The moment you need several servers sharing one permission set, this is the wrong tool and LuckPerms is the right one.

What it deliberately doesn't do

Worth being straight about, because picking this over LuckPerms should be an informed choice:

  • Offline players. Commands target players who are online. Setting someone's role while they're away isn't supported.
  • Multi-server sync. One server, one file.
  • Contexts and tracks. No per-world permissions, no promotion ladders.
  • Temporary permissions. Nothing expires on its own.

Each of those is a feature LuckPerms has and this doesn't. If you need one, use LuckPerms — it's free and it's better at being LuckPerms. This is for the servers that were never going to use any of them.

How it works

Current streak is the number that changes behaviour

Kills and deaths are history — they tell you what already happened and nothing about right now. A current streak is live. It goes up while you're winning and it's gone the moment you're not, which means a player sitting on a good one plays more carefully than they otherwise would.

That's the whole reason both streaks are on the board rather than just a total. Best streak gives you something to chase; current streak gives you something to lose. On an FFA server, where there's no objective other than fighting, those two numbers are most of what makes a session feel like it has stakes.

Everything on the board is a toggle

All seven stats are individually switchable in the config, because the right board depends on the server. A pure deathmatch server might want kills, streaks and K/D and nothing else. A server with rounds cares about wins and losses. Showing everything by default and letting people delete what they don't want is easier than making them assemble it.

The board title and its colours are configurable too — it ships with a purple-to-pink gradient, and both ends are set in the config rather than hardcoded, so it can be made to match a server's existing branding instead of clashing with it.

There's also a seasonal flag, for servers that want to reset the table and start a new competition rather than have month-one players permanently at the top.

Small on purpose

The whole plugin is a few kilobytes. It does one thing — count some numbers and put them on a scoreboard — and it doesn't need a database, a permissions tree or a dependency to do it.

Not everything has to be AegisStaff. A server owner who wants a stats board should be able to drop in a jar, restart, and be finished, and anything that made that harder would be working against the point of it.

Not everything deserves a plugin. These are the tools a live server runs on day to day — handing out crate keys, letting staff post as another player, printing the rules. Small surface, written to sit on top of the plugins rather than duplicate them.

How it works

One data file, five complete rebuilds

Every rank, price, checkout link, perk list, colour code and blurb lives in a single data.js that assigns one object to window.KYRON. Nothing is written into the markup. Each theme reads that object and renders itself from it.

window.KYRON = { ip: "kyron.mygame.host", version: "Java 1.21+", perks: ["Custom prefix on tab", "Rank kit", ...], ranks: [ { name: "Flame", price: 2.50, tag: "Flame", colour: "#FFAA00", mc: "&6", blurb: ... }, ... ] }

Each rank carries its hex colour and the Minecraft colour code the prefix actually renders in, so the chat preview on the site shows the tag in the same colour the player will see it in game. Getting that wrong is the fastest way to a refund request.

A price change is one number, once. Five themes follow. That mattered more than it sounds like it should: the whole point of building five was that the client could change their mind about the look without anyone re-entering nine ranks by hand.

Taking money without a backend

The site is static. There is no server holding card details, no database of orders, and nothing of mine sitting between a player and their bank — checkout is a Stripe Payment Link per product, so the card form is Stripe's page on Stripe's domain.

For a server store that's the right trade. The alternative is running a payment backend for the sake of eleven fixed-price products, and taking on the liability that comes with it. This way the riskiest thing the site does is redirect.

What that leaves is the part players actually get confused by: what happens between paying and having the rank. So the page answers it directly — a "what happens after I pay" section, gift card redemption steps written out, and a support email on every page. Most store tickets are that question, and answering it on the page is cheaper than answering it eleven times a week.

Live player count

The hero shows how many people are on right now, which is the single most persuasive thing a server store can put above the fold, and the fastest way to look dead if it breaks. It degrades to the plain IP rather than to a zero or a spinner when the query fails.

Next to it, one button that copies the IP to the clipboard — kyron.mygame.host, with the raw 46.249.47.73:25006 as the fallback for clients that don't resolve the hostname — and one that opens the Discord. Those two buttons are what the page is for; everything else is underneath them.

Questions I get asked.

Do I get the source code?

Yes, on request. You paid for it. Some clients only ever want the jar and the config, which is fine, but the source is yours if you want it and I won't hold it back as leverage.

What if it breaks after you've delivered it?

If it's a bug in what I built, I fix it. That isn't a support contract with a time limit on it. It's just that shipping something broken and walking away isn't delivering. New features, or making it work on a version that came out later, are new work. The line is simple: if it never did what we agreed, that's mine. If you want it to do something else, that's a new job.

How many revisions do I get?

There's no counter. Iteration is step four of how I work and it's the part that decides whether the thing is good, so I'm not going to charge you per opinion. What does change the price is scope. Rebalancing an ability ten times is iteration. Deciding halfway through that it also needs a GUI and a database is a different plugin, and I'll say so before doing it rather than after.

Can you work with a plugin I already have?

Usually. Building on top of another plugin's API is normal. The Skript tooling on this site drives KyronCrates through its own commands rather than reimplementing it, which is exactly this. What I can't promise is modifying a paid plugin I don't have the source to. Tell me what you're running and I'll tell you honestly whether it's possible.

What do you need from me to start?

Your server software and version, roughly how many players it needs to hold, and a description of what the feature should feel like to the person using it. Not a spec. I'd rather hear "crates should feel like opening something, not clicking a chest" than a list of methods. If you have a competing plugin you like parts of, say which parts. That's usually the fastest way to understand what you actually want.

Will it slow my server down?

It shouldn't, and that's a design constraint rather than an afterthought. Things that run on every block break or every tick get treated differently from things that run when someone types a command. Fresh's Sus and Crysgear both explain where that mattered and what it cost. If you're already running badly before I start, I'll tell you that too. A new plugin isn't going to fix an overloaded server.

How I build.

The item is the save file.

Crysgear keeps an aspect, its tier and its infusion state inside the item's own PersistentDataContainer, not in a database keyed by UUID. Restart the server, move the world, hand the item to someone else. The state goes with it, because it never lived anywhere else.

Assume the server is going to crash.

A crate key is only consumed once the spin has actually started, and the prize lands in the winner's inventory whether they close the menu, disconnect, or the server dies mid-animation. Holograms are non-persistent entities respawned on chunk load, so a hard crash can't leave text floating over an empty field forever.

Admins shouldn't be editing YAML.

KyronCrates has no config worth opening. You build a crate in a menu: drop items in, click the odds up and down, watch the percentages move, close it. The file on disk is an output, not an input.

Adding to it should be boring.

A new Crysgear aspect is one enum constant, one handler class and one line in onEnable. The HUD, the cooldown tracker, the core GUI and /cores info all pick it up without being told.
