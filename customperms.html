CustomPerms

Ranks and permissions without LuckPerms. Four roles out of the box, a coloured star next to every name, per-player permission grants, and a config you can read in one sitting.

Java 21Paper 1.21no dependenciesreplaces LuckPerms

Why it exists

LuckPerms is excellent and most servers only ever use a tenth of it. Contexts, tracks, inheritance graphs, MySQL sync, a web editor — powerful, and all of it sitting on a server whose actual requirement is "give staff a blue name and let them run a few commands".

This does that part and stops. Four roles, a permission list per role, per-player grants on top, and a name colour. One config file, no database, nothing to install alongside it.

Each role carries a label, a star glyph, a hex colour, an order number and its permission list. All five are config values, so the shipped four are a starting point rather than a fixed set — add a fifth by copying a block.

How it works

Inheritance is a list, not a graph

LuckPerms resolves inheritance at runtime — a group points at its parent, that parent points at its own, and the effective set is computed by walking the tree. Powerful, and the reason a misconfigured setup can be genuinely hard to debug.

Here each role simply lists every permission it has, including the ones it shares with the roles below it. Owner's list contains the dev, staff and member nodes explicitly. It's more typing and it duplicates entries — and in exchange, what a role can do is the list next to its name. There is no resolution step to reason about and no way to be surprised by an inherited node you forgot about.

That trade only works because the list is short. At forty roles it would be unmanageable, and at that size you should be running LuckPerms.

Permissions are attachments, rebuilt from scratch every time

Bukkit grants permissions through attachments, and the easy mistake is to add them incrementally and lose track — a stale attachment keeps granting a permission long after it should have gone.

So nothing is ever adjusted in place. Every refresh removes every attachment the plugin is holding for that player, then rebuilds the whole set from their role plus their personal grants. Applying a change and applying it for the first time are the same code path, which means the state after a change can't drift from what a fresh login would produce.

Attachments are tracked per player and dropped when they disconnect, so a long-running server doesn't accumulate references to people who left hours ago.

The star is the point

A permission plugin nobody can see is a permission plugin nobody values. The visible half is a coloured star and role label in front of the player's name, applied to both the tab list and their display name, in the role's own hex colour.

It's the same reasoning as ranks on a store page: people pay for, and care about, the part that other players can see. The permission nodes are what the plugin does; the star is what it's for.

One caveat worth stating plainly: this sets the player's display name, so a chat plugin that builds its own format from scratch will ignore it. On a server already running a chat formatter, the star shows in tab and the chat format stays that plugin's job.

Storage is a flat file, on purpose

Role assignments and per-player permissions live in a data.yml next to the config, written on every change. No database, no connection pool, no driver to install.

For a single server with a normal player count that's the right answer — it's readable, it's editable by hand in an emergency, and it backs up by being copied. The moment you need several servers sharing one permission set, this is the wrong tool and LuckPerms is the right one.

What it deliberately doesn't do

Worth being straight about, because picking this over LuckPerms should be an informed choice:

  • Offline players. Commands target players who are online. Setting someone's role while they're away isn't supported.
  • Multi-server sync. One server, one file.
  • Contexts and tracks. No per-world permissions, no promotion ladders.
  • Temporary permissions. Nothing expires on its own.

Each of those is a feature LuckPerms has and this doesn't. If you need one, use LuckPerms — it's free and it's better at being LuckPerms. This is for the servers that were never going to use any of them.
